## Реализовано

- Необязательный `health_dns` для Linux AWG/VLESS: unicast IPv4 внутри `targets`.
  Пользователь выбирает резолвер; новая DNS-проверка не добавляет встроенного
  публичного адреса. Существующая VLESS-диагностика к `api.ipify.org:443` сохраняется
  и не влияет на DNS readiness.
- Desktop-only DNS probe через VPN backend: UDP53, случайный вопрос под
  `.invalid.`, проверка ID/вопроса/типа/класса/QR/opcode/TC/RCode. Принимаются
  success/NXDOMAIN. Прямого выхода и системного resolver нет.
- Один DNS health worker на VPN-сеанс, проверка сразу и затем через 5 секунд после
  предыдущей, таймаут 2 секунды. Три ошибки переводят в `unavailable`, отдельные
  JSON readiness-события; Stop отменяет и присоединяет worker.
- Восстановление с сохранением TUN/direct, включая режим без per-app.
  Новый VPN публикуется только после успешного DNS-ответа. Неудачные попытки
  используют прежний backoff 3–30 секунд, общий предел попытки 25 секунд.
- SIGHUP по-прежнему меняет только правила приложений; `health_dns` требует
  перезапуска. Старые профили сохраняют прежнее поведение.

## Решения и границы

1. Выбрана проверка обычного DNS через VPN, а не специальный серверный echo:
   работает с внешними провайдерами. Цена — подтверждается только UDP/DNS к
   выбранному резолверу, не TCP/все сайты/выходной IP/рекурсия или криптографическая
   подлинность самого резолвера. Отказ DNS-сервиса
   способен вызвать лишние переподключения исправного VPN.
2. Адрес health должен находиться в выбранных подсетях и применяется только к
   AWG/VLESS. Цена — нужен явно заданный резолвер; прежние профили не получают
   автоматического контроля доступности.
3. Вместо несовместимого полного Windows mobile test binary проверены реальные
   Windows service/engine и отдельный новый тест. Цена — старая проблема
   переносимости серверных fixtures остаётся открытой.
4. Сохранена прежняя диагностика VLESS к ipify; формулировка об отсутствии
   публичного адреса ограничена новой DNS-проверкой. Цена — прежние внешние
   HTTPS-запросы продолжаются, хотя DNS readiness от них не зависит.
5. Трафик допускается при initial checking и первых двух ошибках, чтобы не
   прерывать сеанс при временном отказе. Цена — до третьей ошибки пользователь
   может получать ошибки VPN-трафика без немедленного переподключения.
6. Физические uplink/systemd/providers/REALITY/длительная нагрузка, Windows
   readiness/UI и поведение Android оставлены отдельной приёмке. Цена — этот
   пакет не исключает проблем в этих окружениях; существующее поведение общего
   ядра сохранено.
7. Посторонние dirty-изменения оставлены вне пакета. Цена — эти тесты не
   подтверждают их совместную интеграцию.

При начальном `checking` трафик уже может проходить; при первых двух ошибках
действующий VPN остаётся доступен. `vpn_dns_ready` не означает полной готовности
интернета. Не закрыты физические смены uplink, установленный systemd,
REALITY/внешние провайдеры, нагрузка и Windows remote readiness. Установленные
клиенты и пользовательские профили не заменялись; подготовлены локальные
артефакты, публикация не выполнялась.
