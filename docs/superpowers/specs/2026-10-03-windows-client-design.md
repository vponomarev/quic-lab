# Windows-клиент VPN — проект дополнения к спецификации

> **Актуализация 2026-10-14:** Основной подход к приложениям — [Wintun + определение владельца в user space + direct](2026-10-14-windows-per-app-tun-design.md). Новая спецификация имеет приоритет над противоречащими требованиями ниже, включая дополнение «Приоритет приложений»: собственный WFP-драйвер не обязателен, kill switch отложен, IPv6 не меняем, неопределённый владелец обрабатывается явной политикой. Старые строгие требования оставлены как история решения.

Дата: 2026-10-03. Статус: цели и спецификация согласованы владельцем 2026-10-03; разработка возобновляется. Дополнения владельца от 2026-10-13: VLESS, основа атрибуции приложений, сценарий Roblox; MDM и исследовательская диагностика отложены.
Основание: [общая спецификация](2026-09-30-vpn-product-design.md), текущий проверенный checkpoint cd769e0. Приоритет владельца от 2026-10-03: Android VLESS → мультиплексирование через внешние подключения → подписки. Незавершённая приёмка Android остаётся самостоятельной задачей.

## Цель и исходные требования

Полноценный Windows-клиент с теми же понятиями и пользовательскими действиями, что Android: выходы, профили, автоматический/резервный/отключённый режим, экономия/максимальная доступность, общий бюджет и базовые показатели состояния. Совместимость с исследовательской диагностикой закладывается архитектурно; сам сбор и его интерфейс не входят в основные функции первого выпуска. Собственный сервер необязателен для поддерживаемых standalone-профилей. Начальный целевой вариант предлагается ограничить Windows 11 x64; другие версии и ARM64 не объявляются проверенными до отдельной матрицы.

Общая продуктовая спецификация достаточна для транспортов и политик. Она не определяет Windows-службу, установку драйвера, привязку сокетов, изменение DNS/маршрутов, локальный IPC и распространение обновлений Windows. Эти решения задаёт данное дополнение.

## Подходы

1. **Предлагаемый:** существующее Go-ядро, отдельная привилегированная Windows-служба, Wintun и непривилегированный интерфейс WPF/.NET. Транспортная логика остаётся общей, интерфейс и системная интеграция адаптируются к Windows. Цена — два языка для Windows-продукта; экономия — не переписываем VPN-ядро.
2. Go-служба и интерфейс на Go: один язык, но выбор и проверка desktop UI библиотеки становятся дополнительной задачей; готового интерфейса в репозитории нет.
3. Go-служба и web-интерфейс в desktop-оболочке: возможное переиспользование будущего desktop UI, но добавляются frontend-сборка и граница с web runtime. Для первого Windows-клиента предлагается отложить.

Одинаковый UX означает одинаковые действия, состояния и термины. Это не требует одного UI-фреймворка на Android и Windows.

## Граница процессов

Go-служба владеет адаптером, туннелями, маршрутами, DNS, блокировками и хранилищем конфигураций. Интерфейс запрашивает действия и отображает снимки состояния. UI не запускается постоянно от администратора. Установка/удаление службы и драйвера требуют повышения прав; автозапуск службы не означает автоматического подключения VPN.

Локальный IPC — именованный канал с ограничением доступа службе и явно разрешённому локальному пользователю. Нет слушающего HTTP-порта. Служба проверяет команды и конфигурации; UI не передаёт произвольные команды ОС. Секреты защищены средствами Windows, не попадают в журналы или IPC-снимки метрик.

Закрытие окна оставляет запущенный VPN работать; явная кнопка Stop отключает его и снимает принадлежащие приложению блокировки. Повторный запуск UI подключается к текущему состоянию службы.

## Повторное использование ядра

Сохраняются общие vpnmodel, routing, pathpolicy, trafficbudget, bond, gateway, AWG-движок и поддерживаемый VLESS/Xray backend. Windows-адаптеры реализуют TUN, сети и привязку сокетов. Минимально выделяется используемый несколькими платформами обработчик пакетов; не переносим Android lifecycle и не создаём универсальную платформу плагинов.

Обнаруженное ограничение текущего кода: mobile/gateway_tun.go имеет build tag linux, использует unix.Dup и fdbased Android TUN. Наличие транзитивной зависимости Wintun в go.mod само по себе не означает готовый Windows VPN. Переносимость gVisor/tun2socks/AWG и собственного QUIC fork проверяется сборкой и тестами до обещания поддержки.

## Первое рабочее окно функций

- Импорт существующего профиля из файла/строки и QR-изображения; сканирование камерой не требуется для первого Windows-этапа.
- QUIC и HTTPS с общей сессией; AWG и VLESS как самостоятельные транспорты. VLESS поддерживает TLS и REALITY, импорт vless:// и совместимые параметры текущего Android-клиента: SNI, fingerprint, flow, ключи/short ID и остальные применимые настройки. Паритет означает поддерживаемые режимы нашего Android-клиента, а не все расширения Xray. Перенос сессий между VLESS/AWG и QUIC/HTTPS не обещается. Те же настройки доверия, режимов профиля и применимого ограниченного пула.
- Минимум два независимых выхода. Маршрутизация всего IPv4 или выбранных IP/подсетей. Доменные правила остаются отдельным следующим этапом. Обязателен общий режим «Выбранные приложения через VPN», аналогичный Android: пользователь сохраняет список приложений в настройках VPN; выбранные направляются в назначенный VPN-выход, остальные — напрямую. Roblox — пример приложения в этом списке, без специальной логики для игры. По решению владельца выбор приложений реализуется после выпуска beta самого VPN, последним функциональным этапом перед первым стабильным релизом. Beta работает с маршрутизацией всего IPv4/подсетей и не обещает выбор приложений. Первый стабильный релиз требует приёмки этого режима.
- Один DNS: системный либо через выбранный выход. Назначенный VPN-трафик блокируется при отказе; прямой fallback не разрешён.
- Несколько физических интерфейсов: Ethernet, Wi-Fi, доступный мобильный/USB-канал. Ограниченность сети определяется средствами Windows и может быть явно задана пользователем; название интерфейса не считается доказательством LTE. Привязка транспортных соединений и обход собственного TUN явные.
- Главный экран: подключение/отключение, выходы, активный транспорт/сеть, RX/TX, общий трафик, RTT/jitter, IPv4 и бюджет. Минимальные эксплуатационные журналы нужны для отладки службы и восстановления сети. Расширенный экран Echo, исследовательский сбор, отправка аналитики, DNS/SNI-разбор и UI исследований отложены; совместимость модели с ними сохраняется. Радиоданные отображаются только если платформа действительно их предоставляет.
- Ручное обновление конфигурации по существующему механизму, с проверкой и подтверждением изменений. Правила совместимости общие. Серверная ссылка на APK не предлагается как обновление Windows: для первой тестовой сборки — ручное обновление Windows-пакета; публикация Windows-ссылок требует явного расширения серверных метаданных.

## Приложения, маркировка и сценарий Roblox — дополнение 2026-10-13

Требование владельца: заложить пометку приложений в QUIC/HTTPS-потоках для последующей динамической обработки на сервере. Практический сценарий — отдельно включать VPN для Roblox. Передача идентичности приложения для маршрутизации не должна зависеть от включения исследовательского сбора; она сама по себе не разрешает хранение истории трафика.

Два независимых механизма:

1. Клиент определяет владельца TCP/UDP-потока и выбирает выход до отправки. Подтверждённый владельцем режим: произвольный выбранный список приложений идёт через VPN, остальные приложения сохраняют обычный прямой маршрут. Список сохраняется между перезапусками приложения/службы и редактируется в настройках VPN, как на Android. Roblox — приёмочный пример, а не отдельный переключатель или жёстко заданное правило. Одной серверной маркировкой выбрать приложения для входа в VPN невозможно.
2. Для QUIC/HTTPS предусмотрены расширяемые метаданные приложения, связанные с устойчивыми идентификаторами клиентской сессии/потока. PID не является идентичностью приложения: он переиспользуется. Локальная модель различает экземпляр процесса (PID и время запуска), идентичность приложения и качество определения known/unknown/shared. Полный путь, командная строка и другие лишние сведения не передаются серверу по умолчанию. Windows EXE не выдаётся за Android package ID.

Метаданные согласуются по capabilities/version и совместимы с существующей моделью происхождения наблюдений. Старые серверы продолжают обслуживать VPN без маркировки. Сервер считает сведения утверждением аутентифицированного клиента, а не доказательством подлинности процесса; клиентская метка не расширяет права аккаунта. Динамические серверные правила — будущий потребитель интерфейса, не неявно включённая в первый выпуск функция. VLESS/AWG остаются стандартными протоколами без собственного слоя меток.

Техническая проверка до выбора реализации: Windows-механизм определения владельца и маршрутизации должен работать с короткими TCP/UDP-потоками, UDP без connect, повторным использованием портов/PID и обновлениями игры. Wintun сам по себе не определяет процесс. Возможный механизм на базе WFP/системных таблиц требует отдельной проверки; необходимость собственного подписанного драйвера, если обнаружится, отражается в плане, а не считается решённой. При неизвестном владельце нельзя молча выпускать потенциально назначенный VPN-трафик напрямую; правила unknown и системного DNS определяются до реализации и отображаются явно.

Приёмка режима выбранных приложений: несколько выбранных приложений используют VPN, невыбранное контрольное приложение использует direct; добавление/удаление из списка и сохранение после перезапуска проверяются отдельно. На примере Roblox основной игровой процесс, launcher/обновление и вспомогательные процессы различаются явно; не назначать VPN всем дочерним процессам без правила. Проверить TCP/UDP, обновление пути установки, вход в игру и передачу данных, отказ VPN и отсутствие скрытого direct fallback. Смена правила действует на новые потоки; существующие не переносятся незаметно. Синтетический тест в VM не заменяет финальную игровую проверку на физическом Windows-компьютере.

## Границы фаз — дополнение 2026-10-13

Порядок уточнён владельцем: сначала выпустить beta VPN, затем заняться выбором приложений перед первым стабильным релизом. Сложность атрибуции потоков и поиска приложений не должна задерживать выпуск beta; результат этого этапа нельзя заранее объявлять проверенным.

- Основной Windows-клиент: служба/GUI, сетевое восстановление, профили, QUIC/HTTPS/AWG/VLESS и маршрутизация; beta выпускается без выбора приложений. Режим выбранного списка приложений выполняется после beta, перед первым стабильным релизом; Roblox используется как один из практических сценариев приёмки.
- MDM: фаза 2–3 после завершения основных функций; привязка, права и удалённые команды сейчас не реализуются.
- Исследовательская диагностика: совместимость идентификаторов, метаданных, происхождения и счётчиков проектируется сейчас; сбор, хранение/отправка и интерфейсы — последующая задача с отдельным согласием.

## Изменение системной сети и восстановление

Служба журналирует только собственные изменения. Порядок подключения, добавления маршрутов, DNS и блокировок допускает откат частичной операции. Остановка восстанавливает принадлежащие приложению настройки, сохраняя изменения пользователя и других VPN. Не откатываем всю таблицу маршрутов из старого снимка.

IPv6-туннель пока не поддерживается. При захвате всего трафика нельзя оставлять IPv6 обходом VPN; конкретные Windows-механизмы фильтрации и их область должны быть проверены на стенде. После аварии службы нужна явная процедура восстановления/Stop; никаких обещаний kill switch без тестов аварий, перезагрузки и частично применённых правил.

## Последовательность реализации

1. Проверка переносимости Go-ядра и тесты платформенных границ, без изменения системной сети.
2. Windows-служба, IPC, хранилище и GUI на искусственном backend; проверка lifecycle и ошибок доступа.
3. Один реальный QUIC/HTTPS-туннель через Wintun, ручной Start/Stop, IPv4/DNS и доказанный откат.
4. Два выхода, переключение интерфейсов/транспортов, пул, бюджет, AWG и VLESS TLS/REALITY.
5. Базовые метрики, импорт/обновление профилей, упаковка и приёмка VPN; выпуск beta без выбора приложений. Возможность будущей атрибуции/маркировки сохраняется в архитектуре, но её реализация и исследование Windows-механизмов не блокируют beta.
6. После beta — последним функциональным этапом: исследование определения владельца TCP/UDP-потока и обнаружения установленных/запущенных приложений, затем сохраняемый список «Выбранные приложения через VPN» и маркировка QUIC/HTTPS. Проверить обновляемые пути установки, launcher/вспомогательные процессы и сценарий Roblox; исследовательский сбор не реализуется.
7. Регрессия VPN и маршрутизации по приложениям, упаковка и первый стабильный релиз. MDM и исследовательская диагностика — последующие фазы.

Это порядок получения проверяемых промежуточных результатов, а не отказ от согласованных функций.

## Проверки и ограничения среды

Общие Go-тесты, race/vet и серверные стенды остаются на Linux 192.168.5.214 по ранее согласованному правилу. Windows-сборка проверяет переносимость; работа службы, Wintun, DNS, маршрутов и GUI проверяется на Windows. Linux и кросс-компиляция не заменяют эти испытания.

Перед испытаниями, меняющими сетевые настройки основной рабочей машины, определяем выбранный стенд и способ восстановления связи. Предпочтительно сначала отдельная Windows VM для установки, IPC, TUN и отката; физическое переключение Wi-Fi/USB-сети затем проверяется на целевом Windows-устройстве. Код драйверов/установщиков не запускается только ради подготовки данного проекта.

Критерии: Start/Stop, независимость двух выходов, отсутствие direct fallback, сохранение сессии в заявленных режимах, бюджет без сброса при reconnect, безопасный откат после ошибки и остановки, корректное поведение при закрытии UI, sleep/resume, смене сети и несовместимой версии сервера. До подтверждения этой матрицы Windows-клиент — тестовая версия.

## Ограниченный Linux scope — решение владельца 2026-10-13

Linux-клиент нужен позднее Windows. Сейчас разрешён объём, который проверяет архитектуру общего ядра и ускоряет Windows beta: проектирование платформенных контрактов и минимальный headless стенд с Linux TUN. Это не обязательство выпустить Linux-клиент одновременно с Windows.

Общая часть: жизненный цикл VPN, конфигурация, выбор выходов, транспорты, бюджет, безопасный снимок состояния и модель применения/отката сетевого плана. Платформенная часть: создание TUN, привязка сокетов к интерфейсу, обнаружение сетей, DNS/маршруты/фильтры, хранилище секретов и управление службой. Windows IPC/SCM/DPAPI/WFP и WPF остаются специфичными для Windows. Общие контракты не должны экспортировать Windows HANDLE/SID или Android FD; конкретные адаптеры могут использовать нативные типы внутри себя.

Linux проверяет программные интерфейсы, а не Windows GUI: WPF-экран и Windows-системные операции по-прежнему испытываются в Windows VM. Минимальный стенд запускается на тестовом Linux-хосте в отдельном network namespace с veth/TUN и отдельной таблицей маршрутов. Не изменять основную сеть или SSH-маршрут Linux-хоста. Проверки недоступных возможностей явно пропускаются, не подменяются успешным mock-тестом.

Не входят сейчас: Linux GUI, desktop integration, пакеты дистрибутивов, NetworkManager/systemd-resolved интеграция, постоянная systemd-служба, MDM, выбор приложений и production-поддержка Linux. Если Linux-работа требует этих подсистем или задерживает Windows без конкретного выигрыша, её откладывают; общий контракт можно проверить fake backend и Windows VM.

## Предлагаемый Windows-стенд VirtualBox

Windows 11 x64; ориентир для стенда — 4 vCPU, 8 ГиБ RAM, 80 ГиБ динамического диска при наличии ресурсов хоста. Два адаптера: NAT для интернета и host-only для управления с текущего компьютера. Подсеть host-only выбирается без конфликта с LAN/VPN. Отдельная локальная тестовая учётная запись администратора, OpenSSH Server и вход существующим публичным ключом codex-socks-test; приватный ключ остаётся на хосте. SSH разрешён только со стороны сети управления.

До сетевых тестов — snapshot чистой VM и проверка доступа через консоль VirtualBox. Канал управления по host-only исключается из тестового захвата явно и только на стенде; аварийное восстановление возможно через консоль гипервизора. SSH используется для сборки/установки/журналов; GUI требует интерактивного сеанса через консоль или доступный RDP, SSH не доказывает работоспособность интерфейса. VM на другом физическом хосте потребует отдельной доступной сети управления: host-only доступен лишь её хосту.

## Изменение стенда владельцем — 2026-10-14

Владелец разрешил использовать основной компьютер вместо недоступной VM. Это заменяет прежний запрет на локальные Windows-runtime проверки. Фактическая ОС — Windows 10 Pro x64, 19045; её результаты фиксируются отдельно и не подтверждают Windows 11.

Порядок: тесты общего ядра без сети → UI/IPC с fake backend → тестовая служба → собственный Wintun и маршруты только к тестовым адресам → реальный VPN после проверки отката. Общие Go race/vet остаются на Linux. .NET SDK допустимо разместить в отдельном каталоге разработки без глобальной замены toolchain.

Вместо snapshot VM: журнал точечных изменений, заранее подготовленная независимая локальная команда восстановления и проверка доступа к Linux-стенду/серверу до и после. Служба/адаптер/правила теста имеют собственные идентификаторы. Чужие VPN, ZeroTier, VirtualBox и Hyper-V адаптеры не отключаются. Снимок сети служит для сравнения, а не для безусловного восстановления прежних значений. Сначала проверяется rollback на тестовом маршруте; если принадлежность изменения не доказана, откат не перезаписывает его.

Намеренный BSOD, принудительная перезагрузка ОС и отказ всех физических интерфейсов остаются для VM/отдельного стенда. Непроведённые сценарии сохраняются в матрице, а не объявляются пройденными.

## Приоритет приложений — принято владельцем 2026-10-14

Это дополнение заменяет прежнее откладывание выбора приложений до beta. Следующий контрольный результат: один выбранный exe передаёт TCP/UDP через VPN, остальные напрямую; отказ VPN блокирует выбранный трафик, доступ управления сохраняется. До этого не включать маршрутизацию всего компьютера.

Два режима с независимыми списками: only_selected и all_except_selected. Первый live этап реализует only_selected; обратный режим не активируется до отдельной матрицы отказов. Ручной выбор exe и выбор из запущенных процессов предшествуют автоматическому каталогу игр. Идентичность — канонический Windows WFP AppID, не PID и не имя файла. Дочерний exe не наследует правило автоматически. При замене/переезде файла идентичность перепроверяется.

Внутренние исходящие сокеты транспорта исключаются из повторного захвата. Защищённый канал управления — отдельное административное правило, которое нельзя включить в VPN обычным списком. DNS Windows может исполняться системной службой: атрибуцию DNS выбранному exe нельзя обещать по PID DNS-службы. На первом этапе системный DNS не меняется; DNS внутри выбранного приложения рассматривается как обычный TCP/UDP.

WFP ALE connect/bind redirection требует callout-компонента. Wintun не предоставляет идентичность приложения. Не подменять реализацию сверкой TCP/UDP-таблиц с последующим общим перехватом пакетов: неизвестная принадлежность первого пакета не должна давать прямой выход выбранному приложению. Не выключать Secure Boot, подписи драйверов и не включать test-signing на основном ПК. Выбор распространяемого подписанного драйвера либо VM для собственного драйвера — открытая зависимость; никакого неподтверждённого обещания per-app VPN в UI до live-проверки.

Системная интеграция должна блокировать выбранные IPv6/неподдерживаемые протоколы при активном VPN, а не пропускать напрямую. Явный Stop снимает собственные правила. Авария службы и потеря туннеля не должны автоматически снимать защиту выбранных приложений. Правила только своего provider/sublayer; системные маршруты/DNS на первом этапе не меняются.
