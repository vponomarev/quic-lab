# Windows-клиент VPN — проект дополнения к спецификации

Дата: 2026-10-03. Статус: цели и спецификация согласованы владельцем 2026-10-03; реализация отложена в пользу Android/VLESS.
Основание: [общая спецификация](2026-09-30-vpn-product-design.md), текущий проверенный checkpoint cd769e0. Приоритет владельца от 2026-10-03: Android VLESS → мультиплексирование через внешние подключения → подписки. Незавершённая приёмка Android остаётся самостоятельной задачей.

## Цель и исходные требования

Полноценный Windows-клиент с теми же понятиями и пользовательскими действиями, что Android: выходы, профили, автоматический/резервный/отключённый режим, экономия/максимальная доступность, общий бюджет, диагностика. Собственный сервер необязателен для поддерживаемых standalone-профилей. Начальный целевой вариант предлагается ограничить Windows 11 x64; другие версии и ARM64 не объявляются проверенными до отдельной матрицы.

Общая продуктовая спецификация достаточна для транспортов и политик. Она не определяет Windows-службу, установку драйвера, привязку сокетов, изменение DNS/маршрутов, локальный IPC и распространение обновлений Windows. Эти решения задаёт данное дополнение.

## Подходы

1. **Предлагаемый:** существующее Go-ядро, отдельная привилегированная Windows-служба, Wintun и непривилегированный интерфейс WPF/.NET. Транспортная логика остаётся общей, интерфейс и системная интеграция адаптируются к Windows. Цена — два языка для Windows-продукта; экономия — не переписываем VPN-ядро.
2. Go-служба и интерфейс на Go: один язык, но выбор и проверка desktop UI библиотеки становятся дополнительной задачей; готового интерфейса в репозитории нет.
3. Go-служба и web-интерфейс в desktop-оболочке: возможное переиспользование будущего desktop UI, но добавляются frontend-сборка и граница с web runtime. Для первого Windows-клиента предлагается отложить.

Одинаковый UX означает одинаковые действия, состояния и термины. Это не требует одного UI-фреймворка на Android и Windows.

## Граница процессов

Go-служба владеет адаптером, туннелями, маршрутами, DNS, блокировками и хранилищем конфигураций. Интерфейс запрашивает действия и отображает снимки состояния. UI не запускается постоянно от администратора. Установка/удаление службы и драйвера требуют повышения прав; автозапуск службы не означает автоматического подключения VPN.

Локальный IPC — именованный канал с ограничением доступа службе и явно разрешённому локальному пользователю. Нет слушающего HTTP-порта. Служба проверяет команды и конфигурации; UI не передаёт произвольные команды ОС. Секреты защищены средствами Windows, не попадают в журналы или IPC-снимки метрик.

Закрытие окна оставляет запущенный VPN работать; явная кнопка Stop отключает его и снимает принадлежащие приложению блокировки. Повторный запуск UI подключается к текущему состоянию службы.

## Повторное использование ядра

Сохраняются общие vpnmodel, routing, pathpolicy, trafficbudget, bond, gateway и AWG-движок. Windows-адаптеры реализуют TUN, сети и привязку сокетов. Минимально выделяется используемый несколькими платформами обработчик пакетов; не переносим Android lifecycle и не создаём универсальную платформу плагинов.

Обнаруженное ограничение текущего кода: mobile/gateway_tun.go имеет build tag linux, использует unix.Dup и fdbased Android TUN. Наличие транзитивной зависимости Wintun в go.mod само по себе не означает готовый Windows VPN. Переносимость gVisor/tun2socks/AWG и собственного QUIC fork проверяется сборкой и тестами до обещания поддержки.

## Первое рабочее окно функций

- Импорт существующего профиля из файла/строки и QR-изображения; сканирование камерой не требуется для первого Windows-этапа.
- QUIC и HTTPS с общей сессией; AWG как самостоятельный транспорт. Те же настройки доверия, SNI, режимов профиля и ограниченного пула.
- Минимум два независимых выхода. Маршрутизация всего IPv4 или выбранных IP/подсетей. Доменные правила остаются отдельным следующим этапом; маршрутизация по приложениям не обещается в первой Windows-версии и не объявляется принципиально невозможной.
- Один DNS: системный либо через выбранный выход. Назначенный VPN-трафик блокируется при отказе; прямой fallback не разрешён.
- Несколько физических интерфейсов: Ethernet, Wi-Fi, доступный мобильный/USB-канал. Ограниченность сети определяется средствами Windows и может быть явно задана пользователем; название интерфейса не считается доказательством LTE. Привязка транспортных соединений и обход собственного TUN явные.
- Главный экран: подключение/отключение, выходы, активный транспорт/сеть, RX/TX, общий трафик, RTT/jitter, IPv4 и бюджет. Echo и журналы — дополнительный экран. Радиоданные отображаются только если платформа действительно их предоставляет.
- Ручное обновление конфигурации по существующему механизму, с проверкой и подтверждением изменений. Правила совместимости общие. Серверная ссылка на APK не предлагается как обновление Windows: для первой тестовой сборки — ручное обновление Windows-пакета; публикация Windows-ссылок требует явного расширения серверных метаданных.

## Изменение системной сети и восстановление

Служба журналирует только собственные изменения. Порядок подключения, добавления маршрутов, DNS и блокировок допускает откат частичной операции. Остановка восстанавливает принадлежащие приложению настройки, сохраняя изменения пользователя и других VPN. Не откатываем всю таблицу маршрутов из старого снимка.

IPv6-туннель пока не поддерживается. При захвате всего трафика нельзя оставлять IPv6 обходом VPN; конкретные Windows-механизмы фильтрации и их область должны быть проверены на стенде. После аварии службы нужна явная процедура восстановления/Stop; никаких обещаний kill switch без тестов аварий, перезагрузки и частично применённых правил.

## Последовательность реализации

1. Проверка переносимости Go-ядра и тесты платформенных границ, без изменения системной сети.
2. Windows-служба, IPC, хранилище и GUI на искусственном backend; проверка lifecycle и ошибок доступа.
3. Один реальный QUIC/HTTPS-туннель через Wintun, ручной Start/Stop, IPv4/DNS и доказанный откат.
4. Два выхода, переключение интерфейсов/транспортов, пул, бюджет и AWG.
5. Метрики, Echo, импорт/обновление профилей, упаковка и приёмка.

Это порядок получения проверяемых промежуточных результатов, а не отказ от согласованных функций.

## Проверки и ограничения среды

Общие Go-тесты, race/vet и серверные стенды остаются на Linux 192.168.5.214 по ранее согласованному правилу. Windows-сборка проверяет переносимость; работа службы, Wintun, DNS, маршрутов и GUI проверяется на Windows. Linux и кросс-компиляция не заменяют эти испытания.

Перед испытаниями, меняющими сетевые настройки основной рабочей машины, определяем выбранный стенд и способ восстановления связи. Предпочтительно сначала отдельная Windows VM для установки, IPC, TUN и отката; физическое переключение Wi-Fi/USB-сети затем проверяется на целевом Windows-устройстве. Код драйверов/установщиков не запускается только ради подготовки данного проекта.

Критерии: Start/Stop, независимость двух выходов, отсутствие direct fallback, сохранение сессии в заявленных режимах, бюджет без сброса при reconnect, безопасный откат после ошибки и остановки, корректное поведение при закрытии UI, sleep/resume, смене сети и несовместимой версии сервера. До подтверждения этой матрицы Windows-клиент — тестовая версия.
