# VPN gateway: план реализации

VPN дополняет существующий echo-режим; его UI, метрики и сервер сохраняются.

- Android 11+, IPv4; отдельный foreground VpnService и экран.
- QUIC streams / HTTPS WebSocket + smux v2; общий протокол прокси.
- all apps / only selected / exclude selected / network routing (IPv4 CIDR).
- mTLS: CA клиентов на exit node; PKCS#12 импорт на Android; gateway в одном процессе с echo, на отдельных listeners.
- TCP и DNS в первом сквозном сценарии; UDP DATAGRAM требует отдельной проверки.
- Exit node разрешает только явно заданные подсети назначения; доступ к домашним сетям обеспечивает администратор.
- Домашний DNS, пересечение подсетей и IPv6 вне текущего объёма.
- QUIC мигрирует существующий сеанс; HTTPS восстанавливает туннель для новых соединений.
- После окончательного разрыва туннеля прежние прокси-соединения закрываются.
- Демонстрационная загрузка: ограниченная скорость, ID запроса, журнал завершения/обрыва.
- Тесты: обе транспортные реализации, mTLS rejection, ACL, TCP half-close, остановка, маршруты; сборка Android и регрессия echo.

## Реализовано и проверено

Ветка `codex/vpn-gateway`: общий сервер echo + mTLS gateway, QUIC streams и WSS/smux, Android VpnService, четыре режима IPv4-маршрутизации, импорт P12, TCP/DNS, SOCKS5 для desktop, тестовая загрузка.

Проверены: Go tests/vet на Windows, Linux race tests, TCP half-close, полный ответ после миграции QUIC, mTLS/ACL rejection, реальный TCP и DNS через тестовый TUN, завершение TUN. Android APK и lint собираются.

До стабильного релиза: системный VPN consent, split tunnel и route mode на телефоне; Wi-Fi/LTE и фоновые ограничения Android. Instrumentation-тест маршрутов подготовлен, но без подключённого устройства не запущен.

Произвольный UDP/DATAGRAM и возобновление прокси-сеансов после окончательного разрыва туннеля остаются следующим этапом. IPv6 и домашний DNS исключены по согласованному объёму.

## Несколько серверов

Первый этап: сохранённые независимые профили (сервер, TLS-идентичность, транспорт,
маршрутизация), активен один. Список приложений можно наследовать из общего или
переопределить для профиля. Импорт QR добавляет профиль, существующие не перезаписывает.

Следующий этап — multiple: один Android VpnService/TUN, несколько одновременных
QUIC/HTTPS-туннелей. Пользователь включает профили и сортирует их по приоритету;
при пересечении правил используется первый подходящий профиль. Примеры:
HomeAssistant → дом, мессенджеры/YouTube → второй шлюз, Nextcloud → работа.
До реализации необходимо определить поведение при недоступности выбранного шлюза,
DNS для разных маршрутов и обработку приложений с общим UID. Приоритеты должны
применяться при создании потока, без переноса существующего TCP-сеанса между серверами.


## Отложено: доменная маршрутизация с Fake IP

Решение от 2026-09-26: реализацию отложить. Целевая схема — Fake IP, а не
маршрутизация только по реальным IP из перехваченных DNS-ответов. Функция общая
для QUIC, HTTPS и AmneziaWG; сохранить Echo, профили и текущие режимы VPN.
Портирование на iPhone также отложено по решению владельца проекта.

### Правила и выбор пути

- Точное доменное имя, домен со всеми поддоменами (с проверкой границы имени),
  IPv4 CIDR; действия VPN / напрямую и явное действие по умолчанию.
- Порядок правил определяет приоритет; первое совпадение применяется к новому
  соединению. Существующие TCP/UDP-потоки сохраняют выбранный путь.
- Список приложений остаётся внешним фильтром допуска в TUN. Доменная политика
  применяется к попавшему туда трафику. Основа должна подходить будущему multiple,
  но несколько одновременно активных профилей не входят в первый этап.
- Локальный DNS выдаёт Fake IP и хранит соответствие Fake IP ↔ домен.
  Восстановление домена и выбор правила выполняются на клиенте до выбора транспорта.
- Реальное DNS-разрешение согласуется с выбранным выходом: для direct — через
  физическую сеть, для VPN — через назначенный DNS по VPN. Не использовать
  прямой DNS как неявный fallback при отказе туннеля.
- Базовый совместимый вариант: клиент получает реальный IP через выбранный DNS,
  затем передаёт реальный адрес текущему QUIC/HTTPS/AWG backend. Fake IP не должен
  уходить на обычный VPN-сервер или в Интернет; ответы возвращаются приложению
  в рамках потока к исходному Fake IP.
- Возможная последующая оптимизация QUIC/HTTPS: передавать gateway домен и порт,
  разрешать имя на сервере с учётом транзита. Текущий протокол требует IPv4;
  необходимы согласование возможностей, поддержка TCP/UDP, проверка ACL по
  фактически выбранному адресу и отчёт о DNS-результате. AWG остаётся IP-туннелем
  и не требует нестандартного серверного расширения для Fake IP.

### Диагностика — обязательная часть

Для потока показывать: домен → Fake IP → совпавшее правило → direct/VPN и профиль
→ транспорт → реальный IP:порт. Отдельно: выбранный DNS, путь DNS-запроса,
кеш/TTL, результат разрешения, причина fallback/отказа. Если домен неизвестен,
показывать это явно и указывать применённое правило по умолчанию.
Журнал ограничить по объёму; подробную историю доменов включать явно и не
экспортировать без согласия пользователя.

### Совместимость и проверки

- UDP/TCP DNS, CNAME, отрицательные ответы, TTL и кеш приложений; безопасное
  сохранение/восстановление Fake IP mappings и отсутствие преждевременного
  повторного использования адресов после перезапуска.
- Свой DoH/DoT приложений, Android Private DNS и подключения к IP без DNS:
  документировать ограничения, предусмотреть явную политику неизвестного домена.
- Исключения Fake IP для несовместимых приложений/доменов; диапазон Fake IP
  не должен конфликтовать с пользовательскими подсетями.
- TCP/UDP, QUIC/HTTPS/AWG, direct, смена Wi-Fi/LTE, отказ DNS/VPN, отсутствие
  утечки синтетических адресов и незапланированного прямого выхода.
- IPv4 остаётся первоначальным объёмом; определить обработку AAAA/IPv6,
  не допуская незаметного обхода выбранной политики.

Оценка до технического прототипа: практичная QUIC/HTTPS-версия 2–3 рабочие недели;
единая версия с AWG и проверками совместимости суммарно 3–5 недель для одного
разработчика. Сроки предварительные, реализация сейчас не начата.


## Ближайший этап: несколько одновременных подключений

Приоритет подтверждён владельцем 2026-09-26: реализовать multiple раньше
отложенной доменной маршрутизации. Основной сценарий:

- Профиль A: VPN для выбранных приложений.
- Профиль B: отдельное одновременное VPN-подключение для домашних IPv4-подсетей.
- Один Android VpnService/TUN; несколько независимых транспортных подключений.
  Не создавать несколько конкурирующих системных VPN.
- Профили включаются независимо и сортируются по приоритету. При пересечении
  условий выбирается первый подходящий профиль, как согласовано ранее.
  Чтобы домашняя подсеть имела приоритет даже для приложения из профиля A,
  профиль B нужно поставить выше A; автоматического приоритета CIDR нет.
- Трафик, не совпавший ни с одним правилом, идёт напрямую. При отказе выбранного
  туннеля не переводить его трафик напрямую или в другой профиль неявно.
- Сохраняются самостоятельные настройки профилей и глобальный/индивидуальный
  список приложений. Выбранный маршрут закрепляется за TCP/UDP-потоком.
- Показывать состояние, транспорт, RTT и TX/RX отдельно для каждого активного
  профиля; запуск/остановка одного профиля не должны останавливать остальные.
- Перед реализацией проверить определение приложения для TCP/UDP-потоков на
  поддерживаемых Android, обработку неизвестного UID и общих UID. Системный
  список allowed/disallowed apps относится ко всему TUN и сам по себе не умеет
  распределять приложения по разным туннелям.
- Отдельно определить DNS-политику multiple, исключения для соединений самих
  VPN, взаимодействие с физическими сетями и поведение при изменении правил.
- Проверки: одновременный трафик приложений и домашних подсетей, пересечение
  правил, отказ одного сервера, смена Wi-Fi/LTE, независимая остановка профилей,
  сохранение single-profile и Echo. Доменные правила/Fake IP в этот этап не входят.

### Подтверждённое решение для будущего Fake IP

Владелец принял общий вариант для QUIC/HTTPS/AWG: таблица Fake IP ↔ домен и
восстановление имени находятся на клиенте. Клиент разрешает настоящее имя через
DNS, доступный по выбранному пути (direct или соответствующий VPN), и передаёт
транспортному backend реальный IP. Обычному серверу AWG ничего знать о Fake IP
не требуется. Разрешение домена непосредственно QUIC/HTTPS gateway остаётся
возможной последующей оптимизацией, а не требованием первой версии.


## Прототип multiple — 2026-09-26

Реализован экспериментальный клиент 0.7.0-dev: общий TUN, правила по UID/подсетям,
независимые QUIC/HTTPS/AWG-сессии, direct для несовпавшего IPv4-трафика,
немедленная пауза профиля с блокировкой его маршрутов, выбор общего DNS-профиля,
приоритеты и отдельные метрики. Подробности и ограничения: [multiple-vpn.md](multiple-vpn.md).

Это прототип до испытаний на Android: сборка и Linux-тесты не подтверждают
корректность определения UID и поведения Android при смене сетей. Опубликованный
APK и работающие серверы не обновлялись. Следующий шаг — тестирование на телефоне.
