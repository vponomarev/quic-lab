# Обновление сервера первой фазы

Обновление выполняется повторным запуском `scripts/install-server.py` из нового
архива. Установщик сначала проверяет бинарник и новый `server.json`, затем
сохраняет резервную копию и только после этого заменяет бинарник, unit и конфиг.
Публикация архива, APK и изменение действующего сервера выполняются оператором
отдельно.

## Что сохраняется

В `/etc/quic-lab` сохраняются `admin.json`, `server.json`, `install.json` и
`server.env` при наличии. Данные пользователей и устройств хранятся в
`/var/lib/quic-lab/identities.json`. После проверки конфигурации установщик
останавливает старую службу и сохраняет согласованные копии `identities.json`
и `identities.json.bak` в уникальном каталоге `/etc/quic-lab/backup-*` вместе с
копиями управляемых файлов. Файлы резервной копии имеют режим `0600`, каталог —
`0700`. `state-manifest.json` записывается только после завершения снимка и
содержит наличие файлов, их прежние uid/gid и права. Установщик выполняет
fsync каталога backup и его родителя до запуска новой версии; ошибка fsync
прерывает обновление. Символьные ссылки вместо
файлов identities запрещены; системная ссылка самого StateDirectory допустима.
Рабочий бинарник сохраняется как `/opt/quic-lab/quic-lab-server.previous`.
Каталог данных целиком не копируется: captures, downloads и admin sessions
требуют отдельной резервной копии, если оператору нужна их история.

Установщик сохраняет выбранный режим `frontend` (`nginx` или `direct`) и
сохранённые порты. Он не переносит nginx, не меняет чужой virtual host и не
устанавливает nginx поверх существующей установки. Если домен уже объявлен
другим nginx-сайтом, обновление останавливается до изменения файлов.

## Проверка и откат

Новый серверный JSON проверяется командой нового бинарника с `-check-config` до
замены конфигурации. Ошибка проверки оставляет рабочий бинарник, unit и JSON
нетронутыми. После перезапуска установщик ожидает локальную HTTP-проверку
админки и состояние `active` у `quic-lab.service`.

Если проверка готовности после перезапуска не проходит, установщик останавливает
новую службу, восстанавливает оба identity-файла (включая отсутствие прежнего
`.bak`), их владельцев и права, затем прежние `admin.json`, `server.json`,
`install.json`, бинарник и unit. Старая служба запускается, если до обновления
она работала. При ошибке создания снимка бинарник не заменяется; прежде
работавшая служба запускается снова. Неполный снимок без manifest не пригоден
для восстановления. При ошибке восстановления данных старая служба остаётся
остановленной, чтобы старый бинарник не прочитал новую схему.

Для ручного отката остановите службу и выберите backup, созданный перед нужным
обновлением. Верните соответствующие файлы `/etc` и старый бинарник; `.previous`
относится только к последней попытке обновления. Восстановите identity-файлы
через функции поставочного установщика (нужен Python 3 и права root):

```sh
set -e
python3 - /etc/quic-lab/backup-YYYYMMDD-HHMMSS-SUFFIX <<'PY'
import importlib.util
import sys
from pathlib import Path
spec = importlib.util.spec_from_file_location("installer", "install-server.py")
installer = importlib.util.module_from_spec(spec)
spec.loader.exec_module(installer)
installer.restore_identities(Path("/var/lib/quic-lab"), Path(sys.argv[1]))
PY
systemctl daemon-reload
systemctl start quic-lab
```

Команды выполняются из каталога соответствующего архива, после восстановления
конфигурации и бинарника. Старый бинарник запускайте только со совместимой
схемой из того же backup. Рабочий `identities.json.bak` обновляется при каждой
записи store и не заменяет снимок перед обновлением. Откат теряет изменения
устройств, сделанные после снимка; сохраните новую версию данных отдельно,
если они нужны для последующего восстановления.

Перезапуск может кратко разорвать соединения. Клиент первой фазы должен заново
подключиться к тому же профилю и устройству; identities, ключи, отозванные
устройства и revision конфигурации не должны создаваться заново.

## Поля конфигурации

Используйте имена текущего JSON-контракта. `bond_disconnect_grace_seconds`
задаёт удержание bond-сессии; значение `0` означает серверное значение 120
секунд. Разрешённые VPN cover-SNI находятся в `vpn_sni_names` и проверяются
вместе с реальным `tls_host`. Возможности обновления публикуются в
`capabilities`: `control_version`, `data_version`, `min_android_version_code`,
`features`, `apk_url` и `apk_sha256`.

Установщик сохраняет эти поля при обновлении. Имена `accepted_vpn_sni`,
`update_base_url` и `max_active_devices` не являются полями текущего
`server.json`; лимит активных устройств и URL обновления принадлежат контрактам
админки/D2/D4 и должны изменяться через их поддерживаемые API.

## Проверки перед применением

На Linux выполните:

```sh
python3 scripts/test-install-server.py
go test ./cmd/server ./cmd/demux ./internal/admin -count=1 -timeout=120s
```

Для поставочного архива проверьте SHA256 и содержимое. На одноразовой Linux
машине дополнительно проверьте `systemd-analyze verify`, установку, restart,
upgrade, ошибку валидации, rollback и сохранение существующего nginx-режима.
