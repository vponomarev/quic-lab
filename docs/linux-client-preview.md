# Linux client preview

CLI: QUIC/HTTPS, standalone AWG и VLESS TCP + TLS/REALITY или WebSocket + TLS; IPv4, 1–256 выбранных подсетей или весь IPv4; необязательный выбор VPN/direct по исполняемому файлу приложения. Доступен [GUI preview для управления готовыми подключениями](linux-client-gui.md). Нет MDM и автоматического переключения физической сети. Сам клиент не меняет системные DNS и IPv6-маршруты. Kill switch отсутствует: после остановки VPN трафик снова использует обычную маршрутизацию.

## Запуск

Нужны Linux amd64, /dev/net/tun, iproute2, root и профиль выбранного транспорта. Для QUIC/HTTPS скопируйте client.example.json, замените endpoint на IPv4:port сервера, hostname на TLS-имя, certificate/key/ca на PEM-строки профиля (не пути к файлам). Файл содержит секреты. Пример намеренно не содержит рабочих ключей. Формат AWG/VLESS описан ниже.

```sh
chmod 600 client.json
./quic-lab-client -validate -config client.json
sudo ./quic-lab-client -config client.json
```

Ctrl+C удаляет собственный временный TUN и связанные маршруты. Если в этом сеансе включалась per-app маршрутизация, обнаруженная потеря QUIC/HTTPS запускает повторные подключения с сохранением TUN и direct-соединений на прежней физической сети. Для AWG/VLESS такое восстановление можно включить через `health_dns`, в том числе без per-app (см. ниже). Попытка ограничена 25 секундами, пауза между неудачами растёт от 3 до 30 секунд. VPN-потоки завершаются, новые VPN/DNS-потоки блокируются до восстановления; перехода в direct нет. Без per-app и `health_dns` обнаруженная потеря транспорта приводит к очистке и завершению с кодом 1. Обнаружение потери зависит от таймаутов транспорта. Без `health_dns` AWG/VLESS публикуют готовность локального движка (`readiness: engine_ready`), которая не доказывает доступность сервера; тихая потеря сервера может не запустить восстановление. Журнал выводит состояние и счётчики. `-validate` проверяет структуру, AWG/VLESS-параметры и заданный VLESS CA, но не выполняет сетевую аутентификацию; mTLS-сертификаты QUIC/HTTPS проверяются при подключении.

## Ping и ICMP traceroute

QUIC/HTTPS и standalone AWG передают IPv4 ICMP Echo через VPN с исходным TTL.
Ответы Echo Reply, Time Exceeded и Destination Unreachable возвращаются с реальным
адресом маршрутизатора и восстановленной цитатой исходного запроса:

```sh
ping -4 -c 3 1.1.1.1
sudo traceroute -I -n 1.1.1.1
```

Адрес назначения должен входить в `targets` и разрешённые сервером адреса.
ICMP внутри захвата всегда использует текущий VPN, независимо от per-app правил
TCP/UDP. При отключении или смене VPN ожидающие пробы отменяются; direct fallback
и локальные искусственные ответы отсутствуют. Счётчики VPN учитывают ICMP.

Обычный UDP traceroute и TCP traceroute пока не передают TTL через прокси.
VLESS не поддерживает ICMP. IPv6, фрагменты и пакеты больше MTU 1280 не поддержаны;
максимальный Echo payload без IP options — 1252 байта. Очередь ограничена 32
пакетами, одновременно работают 8 проб с таймаутом 3 секунды. Для QUIC/HTTPS
нужен сервер с ICMP v2 и `CAP_NET_RAW`; старый ICMP v1 допускает только обычный
ping с TTL >=64. Трассировка показывает путь от VPN-выхода; промежуточные узлы
зашифрованного транспорта и UDP-ретранслятор не видны как отдельные хопы.

## Standalone AWG/VLESS

Для AWG используйте `transport: "awg"`, явный внешний IPv4 `endpoint`, `targets` и поле `awg_config` с полным текстом AWG-конфигурации. `AllowedIPs` должны в совокупности покрывать каждую выбранную подсеть. DNS внутри AWG-профиля обязателен для существующей диагностики, системный resolver он не меняет. Поддерживается прежний формат AWG Jc/Jmin/Jmax/S1/S2/H1–H4; произвольные PostUp/скрипты не исполняются.

Для VLESS используйте `transport: "vless"`, явный внешний IPv4 `endpoint`, `targets` и `vless_uri` с импортируемой ссылкой. TLS SNI, WebSocket path/host, REALITY key/short ID берутся из ссылки. Для частного TLS CA допускается PEM в `ca`; REALITY не принимает CA. Пример структуры с заведомо тестовым UUID:

```json
{"transport":"vless","endpoint":"198.18.0.2:443","vless_uri":"vless://11111111-1111-4111-8111-111111111111@vpn.example:443?security=tls&sni=vpn.example&type=ws&path=%2Ftunnel","targets":["192.0.2.2/32"]}
```

Это не рабочий профиль. Числовой endpoint задаёт фактический внешний адрес; hostname ссылки сохраняется для профиля, TLS SNI задаётся отдельно. В режиме выбранных подсетей они не должны захватывать endpoint; в режиме всего IPv4 клиент сохраняет физический маршрут до него автоматически. Материал другого транспорта (`key`, `certificate`, `awg_config` или `vless_uri`) отклоняется при несовместимой комбинации, а не молча игнорируется. Храните весь JSON с правами 0600.

В режиме выбранных подсетей клиент отклоняет перекрытия, захват адреса VPN-сервера и конфликты с существующими маршрутами. Нестандартные policy rules отклоняются в обоих режимах. Физический интерфейс определяется по маршруту до сервера; сокеты привязываются к нему. После смены сети требуется перезапуск. TUN не получает фиксированного IPv4-адреса.

## Весь IPv4

Укажите в профиле `"targets": ["0.0.0.0/0"]`. Клиент добавит только два маршрута
через TUN: `0.0.0.0/1` и `128.0.0.0/1`. Они предпочтительнее обычного default по
длине маски, независимо от его метрики. Исходные default-маршруты сохраняются.
Более специфичные маршруты, включая LAN, Docker и статические сети, продолжают
действовать. Это сохранение существующих маршрутов, а не исключение всех RFC1918
адресов: частные сети без собственного маршрута тоже попадут в VPN.

Если endpoint доступен только через default, клиент сначала добавляет для него
физический маршрут `/32` через прежний шлюз. При уже существующем более
специфичном маршруте исключение не требуется. Обычная остановка и ошибка запуска
удаляют созданные клиентом маршруты. После SIGKILL TUN и оба `/1` удаляет ядро,
но физическое исключение `/32` может остаться; существующие исключения клиент
считает внешними и не удаляет. Смена физической сети требует остановки клиента
и проверки оставшегося исключения, если процесс завершался аварийно.

Нельзя смешивать `/0` с другими `targets`. Уже существующий маршрут `/1`
вызывает отказ до создания TUN, чтобы не вмешиваться в другой VPN. Для AWG
`AllowedIPs` должны покрывать весь IPv4. Системный DNS и IPv6 настраиваются
отдельно; DNS через обычный локальный роутер остаётся в локальной сети.

## Проверка доступности AWG/VLESS

Необязательное поле `"health_dns": "192.0.2.2"` задаёт DNS-резолвер для проверки через VPN. Адрес в примере тестовый: укажите доступный вам unicast IPv4 **внутри `targets`**; для AWG он также должен входить в `AllowedIPs`. Эта настройка разрешена только для AWG/VLESS. Значения по умолчанию нет, системный DNS не меняется. Изменение `health_dns` требует перезапуска, SIGHUP его не применяет.

Клиент отправляет UDP-запрос на порт 53 с новым случайным именем под `.invalid.` непосредственно через VPN, независимо от per-app правил. Прямого выхода или обращения к системному resolver нет. Проверяются идентификатор, вопрос, тип/класс, флаги и код ответа: принимаются success/NXDOMAIN. Успех подтверждает **доступность DNS через VPN**, но не произвольный TCP, все сайты, ожидаемый выходной IP или работу рекурсии самого резолвера.

Отсутствие встроенного публичного адреса относится к новой DNS-проверке. Прежняя диагностика движков сохраняется: VLESS продолжает HTTPS-запросы через VPN к `api.ipify.org:443` для определения выходного IP. Их успех или ошибка не меняют DNS readiness и не являются условием восстановления. Один worker означает одну DNS health-проверку на сеанс, а не отсутствие других диагностических задач.

Первая проверка начинается сразу. После завершения каждой проверки следующая выполняется через 5 секунд; таймаут запроса — 2 секунды. Состояния `readiness`: `checking`, `vpn_dns_ready`, `degraded` после одной/двух последовательных ошибок, `unavailable` после трёх. Успех до третьей ошибки сбрасывает счётчик. Начальный `running` означает запущенный клиент; только `vpn_dns_ready` подтверждает успешный DNS-ответ. При запуске трафик уже может проходить во время `checking`.

После третьей ошибки клиент закрывает VPN-потоки и начинает восстановление, сохраняя TUN и direct. Новый VPN допускается в маршрутизатор только после успешного DNS-ответа; неудачная попытка остаётся недоступной. Это работает и без `app_routing`. Отказ одного DNS-сервиса тоже вызывает восстановление, даже если сам VPN исправен; выберите стабильный разрешённый вам резолвер. До порога ошибок действующий VPN продолжает обслуживать потоки. Остановка отменяет проверку и ожидает завершения её worker.

## Маршрутизация приложений

Добавьте в существующий профиль поле `app_routing` (это фрагмент, не полный профиль):

```json
"app_routing": {
  "version": 2,
  "enabled": true,
  "mode": "only_selected",
  "only": ["/usr/bin/firefox"],
  "except": ["/usr/bin/curl"],
  "unknown": "tunnel"
}
```

Укажите существующие исполняемые файлы своей системы. `only_selected` отправляет через VPN приложения из `only`, остальные — напрямую. `all_except_selected` отправляет через VPN всё, кроме `except`. Оба списка сохраняются независимо. Пути абсолютные, регистр учитывается; символические ссылки раскрываются при проверке и запуске. Скрипт определяется по исполняемому файлу интерпретатора, а не по имени скрипта или командной строке. При отсутствующем поле или `enabled: false` сохраняется прежний режим: весь захваченный трафик идёт в VPN.

Режим действует **только внутри `targets`**; для всего IPv4 используйте `targets: ["0.0.0.0/0"]` с описанными выше исключениями. Direct-сокеты привязаны к физическому интерфейсу. TCP/UDP на порт 53 внутри захвата всегда идут через VPN, включая исключённые приложения. Запросы DNS вне захвата и IPv6 используют прежние системные маршруты. Ошибка VPN не переключает выбранный поток в direct.

`unknown` задаёт поведение, когда приложение определить нельзя: `tunnel` (по умолчанию), `direct` или `block`. При нескольких владельцах сокета правило применяется только при совпадении их решений; смешанные владельцы используют `unknown`. Удалённый работающий бинарник, недоступные данные процесса, ограниченный `/proc`, превышение лимита или таймаута также дают `unknown`. Это определение в userspace с возможными гонками, а не изоляция приложений ядром. Контейнеры и отличающиеся PID/mount namespace не входят в подтверждённую поддержку.

Нужен root с доступом к `/proc/*/fd` и исполняемым файлам других пользователей. `hidepid` и ограничения доступа могут привести к неизвестному владельцу даже у обычных приложений. Поиск ограничен четырьмя одновременными вызовами, 250 мс ожидания, 4096 процессами, 65536 дескрипторами и 16 владельцами. На больших системах это может чаще включать `unknown`; измерения нагрузки на реальном рабочем столе ещё нужны.

После изменения только `app_routing` сохраните JSON с правами 0600 и отправьте `kill -HUP <PID>` запущенному клиенту. Файл открывается заново, в том числе после атомарной замены. Правила, включая включение и выключение per-app, применяются к новым соединениям; уже открытые TCP/UDP сохраняют прежний выход. Изменение других полей, неверные пути, синтаксис или права доступа отклоняются без изменения работающей политики. Событие `reload` сообщает `applied` или `rejected`, не раскрывая содержимое профиля. Для остальных настроек нужен перезапуск, завершающий и VPN-, и direct-потоки.

`-validate` дополнительно проверяет пути и показывает границы захвата. События `app_routing` содержат только суммарные счётчики: direct TX/RX, resolved/unknown/shared, blocked, overloaded, timed_out и DNS; путей и PID в журнале нет.

## Необязательный systemd

Установите бинарник в /usr/local/bin/quic-lab-client, приватный профиль в /etc/quic-lab/client.json (root:root, 0600), приложенный unit в /etc/systemd/system/quic-lab-client.service. После проверки профиля выполните systemctl daemon-reload и systemctl enable --now quic-lab-client. Unit перезапускает процесс при ошибке; он не установлен автоматически на тестовый хост.

Для per-app нужен дополнительный шаблон `packaging/linux/quic-lab-client-per-app.conf`, установленный как `/etc/systemd/system/quic-lab-client.service.d/per-app.conf`. Он добавляет `CAP_SYS_PTRACE`/`CAP_DAC_READ_SEARCH` для чтения сведений о процессах и файлах других пользователей, открывает домашние каталоги только для чтения и использует общий `/tmp`. Базовый unit без этого дополнения намеренно сохраняет прежние ограничения и не обеспечивает определение владельцев других пользователей. Дополнение расширяет привилегии службы; контейнерные/LSM-ограничения оно не отменяет. Синтаксис шаблона проверяется отдельно; полноценная приёмка установленной службы и её перезапусков ещё впереди. Семантика ограничений описана в [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html), доступ к процессам — в [документации procfs](https://www.kernel.org/doc/html/latest/filesystems/proc.html).

## Проверка

scripts/test-linux-client.sh запускается root только на тестовом хосте: две временные network namespace, отдельные сертификаты/ключи, реальные TCP/UDP через QUIC/HTTPS/AWG/VLESS TLS (TCP и WS), очистка TUN/маршрутов, сравнение SSH-маршрута хоста. Пользовательская сеть хоста не захватывается. REALITY не входит в эту локальную TLS-матрицу. Сводный дальнейший план: [все клиенты](client-roadmap.md).

`VPN_PROBE_FULL=1 bash scripts/test-linux-client.sh` проверяет два `/1`, физическое
исключение endpoint, сохранение default/LAN, откат при ошибке второго маршрута и
очистку при остановке. `VPN_PROBE_FULL=1 bash scripts/test-linux-per-app.sh`
проверяет VPN/direct для приложений при физическом default с нулевой метрикой.

`VPN_PROBE_FULL=1 VPN_PROBE_ICMP=1 bash scripts/test-linux-client.sh` добавляет
настоящие Echo 32/1200 байт, отдельный router namespace для Time Exceeded при
TTL=1 через QUIC/HTTPS и отсутствие ответов для VLESS. [Приёмка ICMP](testing/linux-icmp-2026-11-10.md).

`scripts/test-linux-per-app.sh` проверяет два разных исполняемых файла на одном адресе назначения: разные исходные IP для VPN/direct, оба режима списков, захваченный DNS, три политики неизвестного владельца и очистку. [Отчёт per-app](testing/linux-per-app-routing-2026-11-04.md). `VPN_PROBE_LIVE=1` добавляет горячую смену правил и сохранение тех же direct TCP/UDP-сокетов; для QUIC/HTTPS — остановку и восстановление VPN-сервера. `VPN_PROBE_CANCEL_RECOVERY=1 VPN_PROBE_TRANSPORTS=quic VPN_PROBE_LIVE=1` проверяет остановку во время восстановления. [Отчёт жизненного цикла](testing/desktop-live-routing-2026-11-04.md).

`VPN_PROBE_TRANSPORTS="awg vless vless-ws" VPN_PROBE_LIVE=1 VPN_PROBE_HEALTH=1 bash scripts/test-linux-per-app.sh` дополнительно проверяет DNS readiness, потерю/возврат сервера, отсутствие ложного ready при неудачном восстановлении и работу без per-app. Добавление `VPN_PROBE_CANCEL_RECOVERY=1` проверяет остановку во время отказа. [Отчёт DNS readiness](testing/linux-vpn-readiness-2026-11-04.md).
